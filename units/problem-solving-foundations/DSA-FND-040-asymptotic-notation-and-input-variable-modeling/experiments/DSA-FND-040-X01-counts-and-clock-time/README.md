## Why observation is necessary

Only testing square inputs hides the distinction between two independent sizes. Deterministic
counters expose exactly which work was performed when one axis changes. A clock then reveals a
different quantity affected by interpreter and machine behavior. A proof supplies the asymptotic
claim; an actual run supplies the timing observation. Neither should be substituted for the other.

This is supplementary worked material. It does not complete any unsolved practice audit, satisfy a
new curriculum requirement, or record Rahul's learning evidence.

## Hypothesis

Two separate phases have `n + m` body visits; the rectangle has `nm`. Starting from equal positive
dimensions, doubling only one dimension increases the first count by a factor of 1.5 and the
second by 2. Doubling both increases them by 2 and 4 respectively. Timing ratios may differ from
these exact count ratios. In particular, a zero body count need not imply zero total work.

## Environment

The optional timing command reports date in UTC, Python implementation/version, operating-system
details, architecture/processor when available, timer, repeats, and workload. The default command
has no timing component. Both use only the standard library; pytest is needed only for the tests.

The reference run below used CPython 3.14.7 on Linux x86_64 on 2026-08-30. It was executed
separately from the repository checks; unrelated machine activity remains uncontrolled. The
platform API did not report a processor model, so no CPU-model-specific conclusion is supported.

## Controls and measured variables

- Controlled: same interpreter and process, same two functions, fixed integer dimensions, no
  input-list allocation or printing inside timed calls, and the same repeat/number settings.
- Changed: one dimension at a time, then both. All data are deterministic; no random seed is needed.
- Measured: returned body visits and optional repeated elapsed times per complete function call.
- Warm-up: three explicit calls per specimen, plus an earlier untimed count check.
- Timing unit: each reported sample is one batch's elapsed time divided by its call count.
  `min_us_per_call` is the minimum of those batch averages, not the fastest individual call.
- Garbage collection: `timeit` temporarily disables cyclic GC during timing and restores prior
  state afterward. Reference counting, arithmetic, loop control, and function-call costs remain.

## Reproduction command

Run from the unit directory. Use the first command for deterministic counts and the second for
the optional clock comparison:

```bash
uv run --group dev python experiments/DSA-FND-040-X01-counts-and-clock-time/experiment.py
uv run --group dev python experiments/DSA-FND-040-X01-counts-and-clock-time/experiment.py --timing --number 20 --repeat 5
uv run --group dev python -m pytest -q experiments/DSA-FND-040-X01-counts-and-clock-time/test_growth_experiment.py
```

small. Tests assert count and input contracts only; there is no timing-ratio pass/fail threshold.

### How to read this visual

Start at the common input and follow each arrow separately. The labels are predicted event
counts, not measured time or memory. Compare the two different changes to the same baseline.

### Key insight

“Double the input” is ambiguous with two independent dimensions. State which dimensions change
before interpreting a ratio. Testing just the diagonal where `n = m` cannot establish a general
two-variable model.

### Simplification or limitation

The diagram counts only body increments. The rectangle still creates and checks an inner range
for every outer iteration, including when its length is zero. Equal products therefore need not
produce identical timings. Word-cost arithmetic is an analytical assumption, not a claim about
arbitrarily large Python integers.

## Interpretation

1. Direct observation: all six deterministic rows and the four timing-workload pairs returned the
   predicted body counts, including both zero-dimension cases.
2. Direct observation: from `(128, 128)` to `(256, 256)`, the rectangle count became exactly four
   times as large, while the minimum batch-average time became approximately 3.93 times as large.
   The separate-phase count doubled, while its minimum time became approximately 2.29 times as large.
3. Supported inference: event ratios and elapsed-time ratios need not be equal even in this small
   fixed workload. The sample does not isolate which overheads explain the differences.
4. Not established: a finite run cannot prove the asymptotic class, establish a universal crossover,
   or certify a coding-platform time limit. Those count bounds come from the derivation.

The conceptual separate-phase algorithm uses `Theta(1 + n + m)` time; the rectangle uses
`Theta(1 + n + nm)`. Both have constant auxiliary and scalar-output words and no recursion under
the word model. The measurement harness retains `repeat` float samples and printable strings,
which are harness costs rather than space required by the algorithms.

## Threats to validity

- Small functions expose call, validation, and timer overhead; counts omit those operations.
- The order of specimens is fixed, not randomized, so warm caches or machine load can favor one.
- CPU scheduling, frequency changes, interpreter optimizations, and other processes are uncontrolled.
- Counting itself adds Python integer updates; timings are for these instrumented specimens.
- Large-integer arithmetic would invalidate fixed-cost assumptions; this workload uses small values.
- Minimum elapsed time is a noisy workload observation, not a mathematical lower bound.
